# 구현 노트 — PRD v1 대응 및 설계 판단

`PRD-Master.md` / `PRD-v1.md`를 어떻게 구현했는지, 어디서 PRD와 다른 판단을 했는지 정리한 문서다.
실행 방법은 [`../실행안내.md`](../실행안내.md) 참고.

## 1. 기술 스택 — PRD 제안과 다른 점

`PRD-Master.md` §9.1은 스택을 **제안(확정 아님)**으로 두었다. 두 가지를 다르게 선택했고, 근거는 아래와 같다.

| 계층 | PRD 제안 | 실제 구현 | 근거 |
|---|---|---|---|
| 백엔드 | NestJS **또는 FastAPI** | **FastAPI** | 제안 중 하나. 대상 서버에 Node.js가 없고 Python 3.12는 있었다 |
| 엑셀 | SheetJS / **openpyxl** | **openpyxl** (+ `.xls`는 xlrd, `.csv`는 표준 라이브러리) | 제안대로 |
| DB | PostgreSQL 15+ | **SQLite** | 아래 참조 |
| 프런트 | React + TypeScript (Vite) | **표준 ES 모듈 + 순수 CSS (빌드 없음)** | 아래 참조 |
| 배포 | Docker Compose | **파이썬 프로세스 1개** | Docker 미설치. 서버에 파이썬만 있으면 된다 |

### DB를 SQLite로 한 이유

- 대상 규모가 **자산 1,500건 / 동시 관리자 1~5명 / 연간 이력 3,000건**이다.
  실측(자산 2,400건, 이력 5,600건)에서 목록 조회 31ms, 대시보드 27ms로 NFR-04(2초/3초)를 크게 밑돈다.
- NFR-10의 "일 1회 백업"이 **파일 1개 복사**로 끝난다. 운영자에게 별도 DB 관리 부담이 없다.
- DB 서버 설치·계정·튜닝이 통째로 빠진다.
- **이관 여지**: SQL은 표준 문법 위주로 작성했고 DB 접근은 `app/db.py` 한 곳에 모았다.
  규모가 커지면 PostgreSQL 전환이 가능하다. 다만 부분 유니크 인덱스(`WHERE serial_no IS NOT NULL`)와
  `julianday()` 사용부는 손봐야 한다.

> 자산이 1만 건을 넘거나 동시 편집 관리자가 10명을 넘어서면 PostgreSQL 전환을 검토할 시점이다.

### 프런트엔드를 빌드 없이 만든 이유

당시 NFR-01(폐쇄망, 외부 CDN 금지)이 결정적이었다. **이 제약은 이후 해제되었지만 구조는 그대로 두었다.**
React+Vite는 개발 자체보다 배포·재빌드 절차가 부담이 된다(node_modules 수백 MB, 인수인계 시
Node 버전 고정 필요). 화면 15개 규모에서는 표준 ES 모듈로 충분하고, 소스를 고치면 새로고침만으로
반영된다. 차트도 외부 라이브러리 없이 CSS(`conic-gradient`)로 그렸다.

> 제약이 풀렸다고 굳이 되돌릴 이유는 없다. 다만 화면이 더 복잡해지면 프레임워크 도입을 재검토할 수 있다.

#### 판단이 필요했던 항목

- **05-2 / 05-4 복수 선택** — 상세 필터의 자산구분·자산상태·제조사·사업장·부서·운영체제는 체크박스 목록이다.
  같은 항목 안에서 여러 값을 고르면 OR, 서로 다른 항목끼리는 AND로 걸린다.
  URL에는 `status=대기,수리&site=시화,판교` 형태로 실려 북마크·공유가 된다.
- **11-8 대시보드 기간 필터** — PRD가 "기준 기간"의 의미를 정하지 않아 **자산의 구매일**을 기준으로 삼았다.
  요약 카드·사업장·부서·자산구분 집계에만 적용하고, **[조치 필요] 목록은 기간과 무관하게 항상 전체**를 본다.
  "지금 처리해야 할 일"을 기간으로 가리면 알림 기능의 의미가 사라지기 때문이다. 화면에도 이 규칙을 안내한다.
- **03-8 표시 컬럼 / 05-8 검색 조건 저장** — **서버에 계정 단위로 저장**한다(`user_pref` 테이블).
  관리자가 자리를 옮기거나 다른 PC에서 접속해도 설정이 그대로 따라오고, 브라우저 데이터를 지워도 남는다.
  로그인 직후 `GET /api/me/prefs`로 한 번 받아 캐시하고 화면은 캐시를 동기적으로 읽는다.
  저장 키는 화이트리스트(`asset_columns`, `saved_searches`)로 제한하고 항목당 64KB를 넘지 못한다.
  자산번호 컬럼은 식별자이므로 항상 고정 표시한다. 설정을 못 받아와도 화면은 기본값으로 정상 동작한다.
  이전 버전이 `localStorage`에 남긴 설정은 첫 로그인 때 서버로 한 번 옮기고 로컬에서 지운다.
- **04-5 저장 전 확인** — 수정 저장을 누르면 변경된 필드의 `이전 값 → 새 값` 표와 입력한 사유를 먼저 보여주고,
  [저장]을 눌러야 반영된다. 변경된 항목이 없으면 저장하지 않고 알린다.

## 3. 데이터 모델

`PRD-Master.md` §8의 4가지 핵심 설계 결정을 그대로 따랐다.

- **결정 1** — 사용자 정보는 `assignment` 테이블에 행으로 쌓고, `asset.current_assignment_id`가 현재 배정을 가리킨다.
  `assignment(asset_id) WHERE is_current=1` 부분 유니크 인덱스로 **한 자산은 동시에 한 명에게만** 배정됨을 DB가 보장한다 (08-8).
- **결정 2** — `site`/`location`은 `asset`에 둔다. 대기·공용 장비도 물리적 위치를 갖는다.
- **결정 3** — 물리 삭제 없음. 예외는 "등록 후 24시간 이내 + 이력이 `CREATE` 하나뿐"인 오등록 취소뿐이고,
  이때도 `delete_log`에 스냅샷과 사유가 남는다.
- **결정 4** — `employee` 마스터를 두고 배정은 사번을 참조한다.

`user_pref`는 관리자 개인 화면 설정(표시 컬럼, 저장된 검색 조건)을 계정 단위로 담는다.
업무 데이터가 아니므로 이력을 남기지 않고, 계정이 삭제되면 함께 지워진다.

`asset_history`는 `before_json` / `after_json`에 변경 전후 값을 담는 append-only 테이블이다.
관리자가 이력을 직접 쓰는 화면은 없다 — 모든 이력은 등록·수정·배정·회수·상태변경의 부수효과로 자동 적재된다.

## 4. 상태 전환 규칙 (Master §8.3)

`core.py:STATUS_TRANSITIONS`가 유일한 근거다. UI는 이 값을 서버에서 받아 버튼을 구성하고, 서버가 다시 강제한다.

| 현재 | 허용되는 직접 전환 |
|---|---|
| 대기 | 수리, 폐기예정 |
| 사용중 | 수리 |
| 수리 | 대기, 사용중, 폐기예정 |
| 폐기예정 | 폐기, 대기 |
| 폐기 | (없음 — 최종 상태) |

- `사용중 → 대기`는 **회수(FR-09) 액션으로만** 일어난다. 상태 변경으로 사용자 정보가 조용히 사라지지 않게 하기 위함이다.
- `사용중 → 폐기예정` 직접 전환은 차단하고 "먼저 회수 처리가 필요합니다"를 안내한다 (12-6).
- 회수 화면에서는 회수 후 상태를 `대기 / 수리 / 폐기예정` 중에 고를 수 있다 (09-2).

### PRD 도식에 없어 판단한 두 가지 — 확인 필요

1. **`수리 → 사용중`을 허용**했다. Master §8.3 상태표가 수리 중에도 "배정 사용자 유지 가능"이라고 했으므로,
   같은 사람에게 돌려주는 경우를 회수→재배정으로 강제하면 이력이 왜곡된다. 배정된 사용자가 있을 때만 허용한다.
2. **`폐기예정 → 대기`를 허용**했다(폐기 결정 취소). PRD가 명시적으로 금지한 것은
   `사용중 → 폐기예정`과 `폐기 → 기타` 둘뿐이다. 폐기 결정을 되돌릴 수단이 없으면 오조작 복구가 불가능하다.
   사유 입력은 필수이고 `STATUS` 이력이 남는다.

두 항목이 사내 정책과 다르면 `core.py:STATUS_TRANSITIONS`에서 해당 값만 빼면 된다.

## 5. 열린 이슈(OI)에 대한 잠정 처리

PRD가 "추측으로 채우지 않는다"고 한 항목들이다. **확정되면 바꿔야 할 부분**을 남긴다.

| ID | 이슈 | 잠정 처리 | 확정 시 바꿀 곳 |
|---|---|---|---|
| OI-01 | 자산번호 채번 규칙 | **수기 입력을 기본**으로 하되, 등록 화면에 `PC-YYYY-NNNN` 형식의 **[자동 채번] 버튼**을 두었다. 강제하지 않는다 | `routers/assets.py:next_asset_no` |
| OI-02 | 부서 체계 | 사업부 > 팀 **2단계**로 구현 (13-4). 3단계가 필요하면 스키마 변경 필요 | `code.parent_code`, `routers/codes.py:create_code` |
| OI-03 | 임직원 명단 확보 | 엑셀 가져오기로 대응. 갱신 시 `기존 정보 갱신` 모드로 재업로드하면 된다 | — |

## 6. 엑셀 가져오기 설계

PRD의 설계 메모("오류 리포트의 품질이 이 기능의 성패를 좌우한다")를 기준으로 만들었다.

- 오류는 **행 단위로 중단하지 않고 필드별로 모두 수집**한다. 한 번 고치면 한 번에 통과하도록 하기 위함이다.
- 오류 항목은 `행번호 / 컬럼 / 입력값 / 오류사유` 4열이고, 그대로 엑셀로 내려받을 수 있다 (06-7).
- 코드값 오타는 `difflib`으로 유사값을 제안한다 — `데스크탑` → "'데스크톱'을(를) 의도하셨나요?"
- 정규화를 먼저 시도한다: `16GB` → `16`, `2024.03.05` → `2024-03-05`, `ac-de-48-00-11-22` → `AC:DE:48:00:11:22`.
- **오류(등록 차단)와 경고(등록 허용)를 구분**한다.
  - 오류: 필수값 누락, 형식 불일치, 자산구분·상태·사업장 코드 불일치, 파일 내 중복, 논리 위반(사용중인데 사용자 없음 / 폐기인데 폐기일 없음)
  - 경고: 임직원 마스터에 없는 사번, **부서·직급 코드 불일치**
- **부서·직급을 경고로 둔 것은 판단**이다. PRD의 검증표는 코드 오류 대상으로 자산구분·상태·사업장만 열거했고,
  기존 대장의 부서 표기는 마이그레이션 단계 M-3에서 정리할 대상이기 때문이다. 값은 입력한 그대로 저장되고 확인 목록에 표시된다.

배치 되돌리기(06-12)는 **해당 배치로 등록된 자산 중 이후 변경 이력이 `CREATE`/`ASSIGN`뿐인 건**만 삭제한다.
사람이 손댄 자산은 유지하고 그 목록을 알려준다.

## 7. v1에서 하지 않은 것

`PRD-v1.md` §1.2의 제외 항목을 그대로 지켰다 — 자산 실사, 수리·부품교체 이력, 첨부파일, 다중 권한/AD 연동,
이메일 알림, 폐기 결재 워크플로.

다만 **v2 확장이 스키마 변경 없이 되도록** 다음을 미리 넣어 두었다.

- `admin_user.role` 컬럼 (v1은 항상 `ADMIN`) — v3 권한 분리 시 마이그레이션 불필요
- `asset_history.hist_type`가 문자열 — v2의 `REPAIR`/`PART`/`AUDIT` 유형은 값만 추가하면 된다
- `asset.os_eol_date` 컬럼 (Master §7.3에서 v2로 표기된 항목) — 화면 노출은 상세 탭에서만
- `export_log` 테이블 — NFR-09(v2 개인정보 접근 로그)의 출발점

- 인증: 미인증 차단, 오류 메시지, 5회 실패 잠금, 비밀번호 정책, 변경 후 세션 무효화

- 배정/회수: 상태 자동 전환, 1인 다수 자산, 지급일·회수일 순서 검증, 사용 이력 보존
